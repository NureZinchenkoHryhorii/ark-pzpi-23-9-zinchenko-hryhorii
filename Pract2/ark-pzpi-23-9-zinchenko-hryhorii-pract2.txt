3 ОПИС ВИКОНАНОЇ РОБОТИ
3.1 Вступ
Застосування методу рефакторингу передбачає внесення цілеспрямованих змін у структуру коду для усунення виявлених проблем та підвищення його якості. Обраний метод дозволяє оптимізувати логіку, зменшити дублювання, спростити складні конструкції та зробити програму більш зрозумілою. У процесі рефакторингу код перетворюється таким чином, щоб зберегти свою функціональність, але водночас стати чистішим, гнучкішим і зручнішим для подальшої підтримки та розширення.
3.2 Вибір методів рефакторингу
Для практичної частини я обрав свій проєкт із попереднього курсу — гру Mined-Out, класичну міні-аркаду, в якій гравець має пройти мінне поле, орієнтуючись на числові підказки. Попри простоту механіки, старий код виявився досить громіздким: у ньому траплялися надмірні вкладені умови, повторення логіки, «магічні числа» та методи, що виконували занадто багато функцій одночасно.
1.	Remove Setting Method ( Видалення методу встановлення значення) 
2.	Replace Error Code with Exception (Заміна коду помилки на виняток)
3.	Replace Exception with Test (Заміна винятку на перевірку)
3.3 Метод 1: Remove Setting Method
    	 3.3.1 Опис проблеми
У наданому коді класу Player існує метод Move, який безпосередньо змінює внутрішній стан об'єкта, тобто координати X та Y. Це створює проблему, пов’язану з тим, що зовнішній код може у будь-який момент змінити розташування гравця, минаючи логіку контролю, що потенційно призводить до порушення інваріантів або появи некоректного стану. Такий метод є типовим прикладом ситуації, коли внутрішні дані “виставлені на відкритий доступ”, хоч і не прямо, але через змінювальний метод, котрий порушує інкапсуляцію.
	3.3.2 Суть методу
Рефакторинговий прийом Remove Setting Method передбачає вилучення можливості змінювати властивість або внутрішній стан об’єкта через спеціальний метод set, якщо його наявність не є виправданою. На практиці це означає, що або прибирається метод, який змінює значення, або ж логіка змін переноситься у конструктор чи в інший об’єкт, що повинен відповідати за оновлення стану.

	3.3.4 Пояснення обраного методу 
У класі Player метод Move фактично служить сетером для координат X і Y, оскільки безпосередньо встановлює ці значення. Це суперечить ідеї інкапсуляції, оскільки логіка переміщення повинна контролюватися або окремим об’єктом (наприклад, логікою гри), або повинна мати суворі внутрішні правила. Крім того, Player не повинен самостійно встановлювати довільні координати — краще, щоб він рухався тільки відповідно до напрямків, а конкретні координати не задавались напряму. Таким чином, метод Move доцільно видалити, а замість нього створити методи руху на один крок у певному напрямку (Up, Down, Left, Right), які гарантують контрольований і безпечний спосіб зміни стану.

3.3.6	Переваги отриманого коду після застосування методу
Клас Player більше не дозволяє зовнішньому коду безпосередньо встановлювати нові координати, що значно підвищує надійність і передбачуваність логіки переміщення. Методи напрямків руху роблять інтерфейс гравця чистішим і зрозумілішим, виключають можливість стрибків на довільні координати й забезпечують поступове переміщення по полю. Структура коду стає безпечнішою, більш інкапсульованою і зручнішою для подальшої підтримки та розширення.
3.4 Метод 2: Replace Error Code with Exception	
3.4.1 Опис проблеми	
У методі CountNearbyMines класу Minefield при передачі некоректних координат метод не повідомляє про помилку, а повертає 0, що інтерпретується як кількість мін навколо. Таким чином помилка маскується під коректний результат, що створює ризик появи некоректної логіки у програмі. Повернення 0 в цьому випадку фактично виступає роллю коду помилки, оскільки означає не “немає мін”, а “метод не зміг виконати коректний підрахунок”. Такий підхід ускладнює діагностику та відлов помилок. 
	3.4.2 Суть методу 
Прийом Replace Error Code with Exception передбачає заміну повернення кодів помилок (наприклад, -1, null або 0, що несе іншу семантику) на винятки. Якщо метод не може виконати роботу, він повинен не повертати умовне значення, а кинути exception. Це забезпечує надійніший контроль помилок, дозволяє централізовано їх обробляти та робить логіку коду прозорішою. 
	3.4.3 Код до рефакторингу 
1 public int CountNearbyMines(int x, int y)
2 {
3    int count = 0;
4    for (int i = x - 1; i <= x + 1; i++)
5    {
6        for (int j = y - 1; j <= y + 1; j++)
7        {
8            if (mines.Contains((i, j)))
9            {
10                count++;
11           }
12       }
13    }
14    return count;
15 } 

	3.4.4 Пояснення обраного методу 
Метод CountNearbyMines повинен працювати тільки з координатами, що знаходяться в межах поля. Якщо програмі передають некоректні значення, це означає логічний збій вище по програмі. Повернення 0 у цьому випадку ховає помилку і може привести до некоректної поведінки алгоритму або неправильних підказок на полі. Метод Replace Error Code with Exception дозволяє зробити поведінку явною: при передачі недійсних координат метод повинен повідомити про помилку через виняток, а не повертати значення, яке вводить у оману. 
3.4.5 Код після рефакторингу

3.4.6 Переваги отриманого коду після застосування методу 
Після внесення змін метод більше не приховує помилки, що значно підвищує надійність усього процесу обчислень. У випадку передавання недійсних координат розробник або ігрова логіка отримають чіткий виняток, що дозволить швидко знайти проблему. Код стає прозорішим, а логіка — безпечнішою та передбачуванішою. Це також допомагає уникнути потенційних багів, коли дані “виходять за межі” і при цьому виглядають як коректні результати.
	3.5 Метод 3: Replace Exception with Test
	3.5.1 Опис проблеми 
	У методі UpdateGameField кожне завантаження зображення виконується через Image.FromFile без будь-яких перевірок існування файлу. Якщо зображення буде видалене, переміщене або недоступне, метод викине виняток під час виконання програми, що призведе до аварійного завершення гри. У цій ситуації виняток не є ознакою логічної помилки програми — це лише наслідок відсутності попереднього тесту. Тому використання винятку тут недоцільне, і логіку слід переробити так, щоб програма перевіряла умову перед викликом потенційно аварійного методу. 
	3.5.2 Суть методу 
Рефакторинговий прийом Replace Exception with Test пропонує не покладатися на винятки як на інструмент керування потоком виконання в передбачуваних ситуаціях. Замість цього потрібно виконувати попереднє тестування умови, яка може призвести до винятку. Якщо результат тесту негативний, програма повинна виконати безпечну альтернативну дію, не доходячи до моменту, де виник би виняток.

	3.5.4 Пояснення обраного методу
Оскільки відсутність файлу зображення не означає помилку логіки гри, а є лише технічною проблемою, що легко передбачити, ловити такі ситуації через винятки неправильно. Краще перевірити існування файлу заздалегідь. Це зробить поведінку програми передбачуваною, запобігатиме аварійному завершенню та дасть можливість показати альтернативне зображення. Метод Replace Exception with Test саме й застосовується у таких випадках — коли виняток використовується там, де мала б бути перевірка.

	3.5.6 Переваги отриманого коду після застосування методу
Після внесення змін програма перестає аварійно завершуватись через відсутність файлів. Кожне завантаження зображення стає безпечним та контрольованим. Логіка стає передбачуваною, а помилки, пов’язані з ресурсами, обробляються коректно без використання винятків для нормальних робочих ситуацій. Це підвищує стабільність гри й робить роботу з ресурсами набагато надійнішою. 
	3.6 Інструменти автоматизації рефакторингу (Visual Studio) 
У сучасних умовах розробки програмного забезпечення особлива увага приділяється підтримуваності, читабельності та довгостроковій якості коду. Рефакторинг став невід’ємною частиною професійного програмування, а середовище Visual Studio надає широкий набір інструментів, що дозволяють виконувати покращення коду швидко та без ризику порушити його роботу. 
	3.6.1 Rename  
Інструмент Rename дозволяє перейменовувати змінні, методи, властивості, класи та інші елементи проекту без ризику пропустити їх використання. Visual Studio автоматично знаходить усі посилання в рішенні і змінює їх у відповідності до нового імені. Це знижує ймовірність помилок та значно прискорює роботу в порівнянні з ручним пошуком і заміною.
	3.6.2 Extract Method
Extract Method використовується для виділення частини складного методу в окремий новий метод. Це допомагає покращити структурованість і читабельність коду, сприяє повторному використанню логіки та усуває дублювання. Visual Studio сама визначає необхідні параметри і створює метод коректно.  
3.6.3 Extract Interface
Цей інструмент дозволяє автоматично створити інтерфейс на основі існуючого класу, вибравши потрібні методи та властивості. Extract Interface використовують для покращення архітектури, зменшення зв’язності між компонентами та впровадження принципів SOLID, зокрема Interface Segregation та Dependency Inversion.
3.6.4 Move to File / Move Type to Matching File
Даний інструмент використовується для перенесення класу, інтерфейсу або структури в окремий файл, якщо його визначення знаходиться разом із іншими типами. Visual Studio автоматично створює новий файл з коректною назвою та переносить туди відповідний тип, що підвищує організованість проекту та полегшує навігацію.
3.6.5 Remove Unused Usings
Remove Unused Usings автоматично видаляє непотрібні підключення простору імен у початковій частині файлу. Це допомагає зменшити захаращеність коду, прискорює компіляцію та робить структуру файлів чистішою і зрозумілішою.
3.6.6 Code Cleanup та Analyzer-и	
Visual Studio має вбудовану систему Code Cleanup, яка дозволяє одним натисканням застосувати встановлені правила стилю, форматування та виправити дрібні проблеми. Крім цього, вбудовані аналізатори (Roslyn analyzers) автоматично виявляють потенційні проблеми в коді, рекомендують рефакторинг та забезпечують дотримання стандартів. Це дозволяє підтримувати якість коду на високому рівні та знижує кількість помилок на ранніх етапах.


4 ВИСНОВКИ
У ході виконання практичної роботи було проведено комплексний аналіз та рефакторинг програмного коду, що дозволило підвищити його якість, знизити кількість прихованих проблем та покращити архітектурну структуру проєкту. Первинний аналіз показав наявність фрагментів, які хоча й забезпечували роботу програми, але мали суттєві потенційні недоліки щодо розширюваності, надійності та підтримуваності. Застосовані методи рефакторингу дозволили продемонструвати, як невеликі покращення окремих частин коду впливають на загальну якість програмного продукту.
Першим було реалізовано метод Remove Setting Method, який був застосований до методу Move класу Player. Виявлено, що цей метод безпосередньо змінював координати об’єкта через зовнішні виклики, порушуючи інкапсуляцію та створюючи зайві можливості для помилок. Рефакторинг дозволив обмежити неконтрольовану зміну стану об’єкта і зробив код більш безпечним, структурованим та передбачуваним.
Другим було впроваджено метод Replace Error Code with Exception, що був продемонстрований на прикладі коду перевірки досяжності цілі стріли. Початкове використання числових кодів помилки ускладнювало логіку та могло призвести до нерозуміння причин відмови. 
Третім застосованим методом став Replace Exception with Test, який дозволив позбутися використання винятку там, де ситуація не була помилковою, а передбачуваною частиною поведінки програми. За допомогою попередньої перевірки (умовного тесту) було покращено читабельність коду, знижено навантаження та виключено зайві обчислення, тим самим зробивши логіку більш чіткою та оптимальною.
Окрему увагу в роботі було приділено інструментам рефакторингу Visual Studio, таким як Rename, Extract Method, Extract Interface, Move Type to File, Remove Unused Usings, Code Cleanup та Analyzer-и. Ці інструменти дозволяють значно спростити процес покращення коду, уникнути типових помилок та автоматизувати рутинні дії. Застосування таких засобів у сучасній розробці є критично важливим, оскільки підвищує продуктивність та забезпечує однакові стандарти написання коду в команді.
Підсумовуючи виконану роботу, можна зробити висновок, що рефакторинг — це не разова дія, а безперервний процес, який допомагає підтримувати програмний продукт у якісному стані. Проведений аналіз та виконані покращення показали, що навіть невеликі фрагменти коду можуть значно вплинути на стабільність та масштабованість системи.
